# Ultrareview findings (src/ only, mvp 802bf92)

Cloud ultrareview of all of `src/` (27 files, 7,702 lines) via branches `review-base...review-src`. 10 findings, each with the reviewer's own verification. Numbers below are used by the fix agents.

1. **[normal] Exactly-once: a full Restore's wipe doesn't invalidate the Checkpoint** (src/restore.ts ~141–147, src/checkpoint.ts). With `changelogFirst`, the wipe runs in a store transaction whose commit doesn't call `dirty()`, so the old `.checkpoint` still lists the store as clean at offset X. If the Checkpoint offset was outside the Changelog (recreated topic, unclean-leader truncation), the store is wiped and a full Restore starts; if that Restore is cancelled (rebalance, stop) or the process crashes, the next start (once the Changelog has grown past X) applies only records after X onto a wiped or half-restored store → keys last written before X silently missing. At-least-once is safe. Fix: the wipe of a full Restore must make the Checkpoint unclean (remove the file or drop the store's entry) regardless of `changelogFirst`.

2. **[normal] Store keys built differently at write time and at Restore** (src/restore.ts ~129, src/state-store.ts ~156/202, src/store-key.ts ~104). Write: `isOrderedValue(k) ? k : SerializedKey(serialize(k))`. Restore: `encode(deserialize(changelogKey))`. Keys whose Serde round-trip changes their JS type (Date with `serdes.json` → string; NaN/Infinity with json → null; lone-surrogate strings with `serdes.string` → U+FFFD) are restored under a different store key: `get` misses, aggregates restart, `all()`/`range()` show duplicate logical keys, deletes don't remove the restored entry. Fix: derive the store key identically on both paths (e.g. always from the Serde round-trip of the key, or reject keys whose round-trip changes them).

3. **[normal] Same-PID staleness breaks containers sharing a state directory** (src/state-directory.ts ~319–325, `isStale`: `if (lock.pid === process.pid) return lock.incarnation !== incarnation`). Containers on one host typically all run as PID 1 in their own PID namespace and share the kernel boot_id, so each treats the other's live Task and App Process ID locks as stale → same App Process ID → same transactional IDs → mutual fencing, crash loop; Task locks bypassed → two owners of one Task's SQLite stores. Regression from the same-PID restart fix. Fix: lock identity unique across PID namespaces with a liveness check that doesn't rely on PID equality; at minimum document sharing a stateDir across PID namespaces (containers) as unsupported, and detect it where possible.

4. **[normal] Async listener / metrics-sink rejections crash the process** (src/observability.ts ~287 `Listeners.emit`, ~350 `recordMetric`). try/catch only catches sync throws; a rejected Promise from an async listener or `record()` is unhandled → Node exits. Docs promise these errors are ignored. Fix: if the return value is thenable, attach a no-op `.catch` (as `handleError` in error-handlers.ts already does).

5. **[normal] Unbounded bytes per send** (src/worker.ts ~1336 at-least-once `producer.send({ messages: outputs })`, ~1407–1414 exactly-once `#send`). The client writes one record batch per partition per send; with 1000-record batches and ~1 KB values a single partition's batch exceeds the broker's max.message.bytes (~1 MB) → MESSAGE_TOO_LARGE produce error → app fails and crash-loops on the backlog. Fix: cap each send by accumulated bytes (and/or count) and split into several sends; `producedOffsets` already handles several base offsets per partition.

6. **[normal] Exactly-once transactions can outlive the transaction timeout** (src/worker.ts ~233–236; `#readBatch`, `#commit` awaiting `Promise.all(this.#work)`). Timeout = commitIntervalMs + 10 s, but a batch's transaction has no time bound: async Processors queued behind each other (e.g. 1000 × 15 ms) exceed it, the broker aborts, the later send/commit fails with a fencing/epoch error that `isRebalanceError` doesn't match → app goes to `error` instead of abort-and-replay. Fix: keep a batch's transaction shorter than its timeout (bound queued work by time / make the timeout configurable and enforced) and treat a timed-out transaction as abort-and-replay, not fatal. Update docs/delivery-guarantees.md "Async Processors stretch transactions".

7. **[normal] Full-Restore wipe loads the whole store into memory** (src/restore.ts ~143–146: `for (const key of Array.from(store.all(), ([key]) => key)) store.delete(key)` in one transaction). OOM or a long blocked event loop (missed heartbeats → rebalance) on large stores; runs after every unclean stop under at-least-once. Fix: a store-level `clear()` (SQLite `DELETE FROM entries` or recreate the file; in-memory: new map) used by the wipe; add it to the State Store interface and contract suite.

8. **[normal] Null/undefined store keys accepted by the Test Driver, rejected on Kafka** (src/state-store.ts ~205–209: the guard only runs when a Changelog exists; the Test Driver has none). Fix: reject null/undefined keys whether or not a Changelog is present.

9. **[nit] Non-integer timestamps accepted by the Test Driver, throw on Kafka** (src/worker.ts ~1559 `BigInt(record.timestamp)`, src/windows.ts ~102 `BigInt(window.start)`). Fix: validate (or normalize) timestamps once where records enter the graph (ctx.forward / the sink in task.ts) so both runtimes behave the same.

10. **[nit, deferred → ticket 32] At-least-once does several fsyncs and a FULL WAL checkpoint every commit** (src/checkpoint.ts ~180–192; every 100 ms per Task with stores). Performance/design: write Checkpoints every N records/seconds or on close/revoke, and flush only changed stores.
