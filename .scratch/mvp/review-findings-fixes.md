# Adversarial review of the fix commits (0150f80..62da2c9)

Finders at high effort, one skeptic per finding at medium effort. 8 findings, 7 survived, 1 refuted.

## 1. [P1] Timer-only transactions are still unfenced for a Task whose records were all skipped by its stable offset (fencingOffsets only knows offsets this Worker committed itself)

- Area: ownership-fencing (claimed P1, reproduced: False)
- Files: src/worker.ts:1259-1273 (fencingOffsets skips partitions missing from #committedPosition), src/worker.ts:1115, src/worker.ts:928-941 (#takeStarted puts starting.stable only into #position, never into #committedPosition), src/worker.ts:1417 (no offsets means no addConsumer/TxnOffsetCommit at all), docs/delivery-guarantees.md:20

**Scenario:** Exactly-once. Worker B takes Task 3 over while the previous owner A's transaction (offsets up to 200) is still open. B's stream starts from the non-stable committed offset 150 (the client reads OffsetFetch without requireStable, see src/stable-offsets.ts header), so B holds records 150..199. The StableOffsetReader then returns 200, #takeStarted moves #position to 200, and #accepts drops every held record. Task 3 is now in #tasks, but this Worker has processed and committed nothing for it, so #committedPosition has no entry for partition 3. The partition is quiet, and a wall-clock punctuator the Processor scheduled when it was constructed fires in #commit and writes outputs and Changelog records. contributors={3}, lastRead=[], and fencingOffsets returns [], so offsets.length===0. The transaction commits with no TxnOffsetCommit, so there is no generation or member check. If B has meanwhile been dropped from the group (GC pause or session timeout, so it is a zombie it has not noticed yet) and C now owns Task 3, B's timer-driven outputs and Changelog-3 writes still commit next to C's.

**Impact:** This is the zombie timer-write gap the fix was meant to close (Codex finding 2), and it is still open in this window. Duplicate outputs and conflicting Changelog records get past exclusivity, and the docs say otherwise: 'every transaction commits consumed offsets ... A Task that only wrote from a timer ... gets its committed offsets committed again'. The window needs a takeover during the previous owner's open transaction, a quiet partition, a wall-clock timer, and a membership loss B has not noticed.

**Suggested fix:** When a started Task is taken over, seed the fencing source from its stable committed offsets: in #takeStarted, also set #committedPosition (or a separate per-Task 'known committed' map) from starting.stable when it is higher than what is there. #forget already clears it on loss. Alternatively, if a timer-only contributor has no known committed offset, either refuse to commit its writes (abort, or defer the timers until a record is committed) or fetch its committed offset first. Add a CommitCycle-level test where a timer-only Task with no committed offset must still get an offset into the transaction.

**Skeptic's evidence:** I could not refute this. Reading the code confirms the gap, and it is wider than the claim says, because no takeover race is needed.

- **Where the fencing source gets its offsets:** `#committedPosition` is written in only one place, src/worker.ts:1151, after a successful commit of records this Worker read itself. `#rewind`, `#abortBatch` and `#forget` copy it or delete from it but never seed it. `#takeStarted` (920-945) writes `starting.stable` into `#position` only.
- **Why fencing comes back empty:** `fencingOffsets` (1259-1273) loops over `committedPosition` alone. So any Task in `#tasks` that has committed nothing on this Worker gets no fencing offset. The simplest case is a newly assigned quiet partition: the stream starts at the previous owner's committed offset and no records arrive.
- **Why the timer write still counts:** `fireWallClockTimers` runs for every Task in `#tasks` (1093-1096). Processors are created when the Task is created (task.ts:306), so a wall-clock schedule exists from the start. Timer outputs call `#contribute` (1016), so the Task is listed in contributors, yet `fencing` is `[]`.
- **Why nothing in the transaction fences it:** in `ExactlyOnceCommitter.commit` (around 1414-1430), `offsets = [...lastRead, ...fencing]`. When that list is empty, the code skips `addConsumer`/`addOffset`, so there is no TxnOffsetCommit and the coordinator never checks generation or member. The produce path still begins the transaction and commits it.
- **No other fence applies:** `transactionalId` is the per-Worker `workerId` (streams-app.ts:684), so when C starts its producer, B's producer epoch is not fenced. `ownedThroughout` only catches losses B has already noticed.

So a zombie B with a quiet Task 3, and no other partition that has records in the same transaction, commits timer outputs and Changelog-3 writes with no broker-side fence. That contradicts docs/delivery-guarantees.md:20. I rate it P1 rather than lower because it breaks an exactly-once exclusivity guarantee the docs make. The window is narrow: a quiet partition, a wall-clock timer, and a membership loss B has not yet noticed.

What I could not run: I wrote a unit test asserting `fencingOffsets([3], [], new Map())` returns `[]`, at /Users/igorshalygin/.claude/jobs/e36bc646/tmp/fence.test.ts. The vitest run timed out (most likely because of `--root /`), so this rests on reading the code, not a passing test.

## 3. [P2] Linux wall-clock step of more than 120 s makes a live process's locks look stale, so a second process takes them over and the lock has two owners

- Area: lock-protocol (claimed P1, reproduced: True)
- Files: src/state-directory.ts:52 (BOOTED = Date.now()/1000 - uptime()), src/state-directory.ts:259-266 (isStale boot check runs before the PID check)

**Scenario:** Linux host, one shared stateDir (supported per docs/operations.md:20). On Linux, libuv's os.uptime() reads /proc/uptime (CLOCK_BOOTTIME), but Date.now() is CLOCK_REALTIME, so BOOTED moves with every wall-clock step. Process A starts. Then chrony/ntpd steps the clock by more than 120 s; typical causes are a VM resumed after host sleep, a board with no RTC, a manual `date -s`, or a service started before time-sync.target. Process B then starts, and its BOOTED differs from the `booted` in A's lock files by more than BOOT_TOLERANCE_S. B reads A's live `processes/<id>.lock` and Task `.lock` files, and isStale returns true without checking the PID. B claims them, removes them and links its own. B now has A's App Process ID (the same transactional IDs) and opens the SQLite stores and Checkpoint of Tasks that A still has open. Not reproduced here: macOS derives uptime from kern.boottime, which the kernel adjusts on clock steps, and that matched in a check on this machine.

**Impact:** Two Workers in different processes own the same Task directory at once and write the same SQLite stores and Checkpoint. A is also fenced unexpectedly through the shared transactional ID. This breaks exactly the exclusivity the new claim protocol is meant to guarantee.

**Suggested fix:** Use a stable boot identifier instead of a value computed from the wall clock: /proc/sys/kernel/random/boot_id on Linux, and sysctl kern.bootsessionuuid or kern.boottime on macOS. Alternatively, compare the boot only by an ID and fall back to the PID check otherwise.

**Skeptic's evidence:** Code is as claimed. src/state-directory.ts:52 sets `BOOTED = Math.round(Date.now()/1000 - uptime())` once, at module load. isStale (src/state-directory.ts:256-266) checks only `lock.pid === process.pid` first, then returns true when |lock.booted - BOOTED| > 120, and never reaches the `process.kill(pid, 0)` liveness check. Nothing rewrites or refreshes a lock's `booted` after it is taken (it is written once at :166). On Linux, libuv's uv_uptime reads /proc/uptime (CLOCK_BOOTTIME, which falls back to clock_gettime(CLOCK_BOOTTIME)), and that clock does not follow wall-clock steps. Date.now() is CLOCK_REALTIME. So a process started after a wall-clock step of more than 120 s computes a BOOTED that differs from the value in locks written by a process started before the step. docs/operations.md says processes on one host may share a state directory. Repro: /Users/igorshalygin/.claude/jobs/e36bc646/tmp/bootstep.test.ts, run with `npx vitest run bootstep --root <tmp>`, passes. It writes processes/aaaaaaaaaaaa.lock with pid = process.ppid (a live process that is not us) and booted = current BOOTED - 200, which simulates the step. claimProcessIdentity then takes that ID even though the holder is alive. The same tryLock/isStale path is used for Task `.lock` files, so a Task directory can be taken the same way. The clock step itself was simulated, not performed, because this is macOS. Severity is P2 rather than P1: it needs a wall-clock step of more than 120 s between the starts of two processes that share a stateDir. That is rare, but the impact when it happens is real: two processes hold the same lock.

## 4. [P2] A restart with the same PID (normal in containers) never takes back its old ID and waits forever on its own dead process's Task locks

- Area: lock-protocol (claimed P2, reproduced: True)
- Files: src/state-directory.ts:184-187 (same pid + holder returns `reentrant`), src/state-directory.ts:260 (`lock.pid === process.pid` is never stale), src/state-directory.ts:68-71, src/state-directory.ts:139 (unlockTasksOf matches only the current processId prefix)

**Scenario:** Kubernetes or Docker with a persistent or emptyDir stateDir; docs/operations.md:44 recommends a persistent state directory. The Node process (often PID 1, or another fixed PID from the same entrypoint) is OOM-killed or SIGKILLed, so the `processes/<id>.lock` and Task `.lock` files stay behind with that PID. The container restarts in the same kernel, so the boot time matches, and gets the same PID. In claimProcessIdentity, tryLock finds pid === process.pid and holder === id, returns reentrant=false, and the process creates a new random ID. Every Task lock `<oldId>/worker-n` has pid === process.pid, so isStale returns false, and lockTask polls until giveUp. unlockTasksOf(newId) never clears these locks either. Reproduced in-process with /Users/igorshalygin/.claude/jobs/e36bc646/tmp/pidreuse.test.ts: lockTask for the restarted holder returns false, and `.lock` still names the old holder. The same happens without containers whenever a dead holder's PID is reused by any live process on the host: the lock stays non-stale until that unrelated process exits.

**Impact:** A stateful Task stays blocked until the volume is wiped by hand, and every further restart repeats it. The old transactional IDs are also not reused, so the dead process's open transactions are aborted only by timeout.

**Suggested fix:** Make the lock name the process instance, not just the PID. Put a per-start incarnation nonce (generated once in the main thread and passed to the workers) or the process start time in each lock. A lock with this PID but another incarnation counts as stale, and for other PIDs, compare the start time when it can be read.

**Skeptic's evidence:** I could not refute this; the code paths are as claimed. In src/state-directory.ts, tryLock returns `reentrant` whenever the lock has the same pid and the same holder. claimProcessIdentity calls it with reentrant=false, so the old ID is skipped and a new random ID is created. isStale (around line 260) returns false at once when `lock.pid === process.pid`. A Task lock `<oldId>/worker-n` is neither reentrant for `<newId>/worker-n` nor stale, so lockTask (called from src/worker.ts:899) polls until giveUp. unlockTasksOf, called only at src/streams-app.ts:780 on stop, matches only the `${processId}/` prefix of the current ID, and nothing else clears locks at start. The lock records only holder, pid, booted and nonce, and the nonce is never compared. So a new process with the same PID and boot time cannot be told apart from its dead predecessor. That happens on a container restart, where Node is often PID 1 and the boot time is the host kernel's. emptyDir and persistent volumes keep the files across container restarts, and docs/operations.md recommends a persistent state directory. I ran /Users/igorshalygin/.claude/jobs/e36bc646/tmp/pidreuse.test.ts (`npx vitest run --root <tmp> pidreuse.test.ts`), which simulates this in one process with identical pid and boot time. Output: old id aae5e83b2f1f, restarted id d0875e5870db, `restarted got task lock: false`, and `.lock` still holds {"holder":"aae5e83b2f1f/worker-0","pid":45920,...} after unlockTasksOf(restarted.id). The second part of the claim also holds: on a host, a PID reused by an unrelated live process keeps the lock non-stale (process.kill(pid,0) succeeds) until that process exits. The impact is a Task blocked indefinitely until someone intervenes by hand, and old transactional IDs are not reused, so P2 is reasonable.

## 5. [P3] docs/limitations.md still says stale-lock takeover can leave two owners, contradicting the new claim protocol

- Area: lock-protocol (claimed P3, reproduced: False)
- Files: docs/limitations.md:20, src/state-directory.ts:27-32

**Scenario:** The fix commits add the limitation that "taking over the stale lock of a dead process can race ... except in a tiny window where both believe they hold the lock". That describes the removed rename-based takeover. Commit 465b0c3 replaced it with claim files and now documents in the source header that the lock is exclusive throughout.

**Impact:** The user-facing docs give the wrong guarantee: they understate the fixed behaviour and recommend against a supported setup for a reason that no longer applies.

**Suggested fix:** Remove or rewrite the limitation line, for example by keeping only the PID and boot-time caveats above.

**Skeptic's evidence:** At HEAD, docs/limitations.md:20 still says that taking over a dead process's stale lock "can race ... the loser notices, except in a tiny window where both believe they hold the lock. Prefer one state directory per process." The line was added in 6fd4abe. The file was last touched in 0c66209, and both commits come before 465b0c3. Commit 465b0c3 ("Take stale locks over through a claim, so a lock never has two owners") replaced the rename-based takeover and changed only src/state-directory.ts and its test, not the doc. The new header comment at src/state-directory.ts:27-32 says the takeover "keeps it exclusive throughout, however many contenders race". The code backs that up. In tryLock (around src/state-directory.ts:170-200), a lock is created only by a hard link, which fails with EEXIST if the name already exists. A stale lock is removed only by whoever holds its claim (.lock.<sha256(content)>.claim, taken the same way), and only if a re-read still finds the same nonced content. The holder of a stale lock is dead, so no one else can replace that content while the claim is held, and the read-then-remove leaves no window with two owners. The PID-reuse and boot-time caveats are separate issues and are not what the doc line describes. So the limitation describes the behaviour the fix removed: it understates the guarantee and still tells users not to share a stateDir for a reason that no longer applies. This is a doc-only inconsistency, so P3.

## 6. [P2] Rolling back Stream Time for a skipped record does not undo window expiry, so expired windows reopen with partial aggregates

- Area: store-task-dsl (claimed P2, reproduced: True)
- Files: src/task.ts:373-386 (before/streamTime rollback in onError); src/streams-app.ts:1137-1145 (aggregation calls expire() before update); src/streams-app.ts:1031-1050 (place()/expire() use task.streamTime(), keptFrom)

**Scenario:** A windowed aggregate uses tumbling('1s'), the processing error handler returns 'continue', and the aggregator throws on a bad value. Pipe a:'x'@100, a:'y'@200, b:'z'@300, then b:'bad'@90000. For that last record the Task advances Stream Time to 90000. The aggregation's expire() then deletes windows a@0 and b@0 from the store and writes their Tombstones to the Changelog, and only after that does the aggregator throw. The handler skips the record and c76ae99 rolls Stream Time back to 300. Next, pipe a:'w'@400. place() compares against the rolled-back Stream Time (400), so the record is not late. Window a@0 is recreated from scratch and emits a@0='w', replacing the earlier final value 'xy'. b@0's 'z' is gone for good. keptFrom still holds the value from 90000, so the reopened window is not looked at for expiry again until Stream Time passes that point. I reproduced this with the Test Driver: output ends with {key:'a@0',value:'w'} and the store holds only [a@0,'w']. Before this commit, a:'w'@400 was dropped as late.

**Impact:** Windowed results are silently wrong: a window that already closed and emitted can reopen and emit a smaller aggregate that replaces the correct one downstream, and earlier aggregates are lost. Stream Time no longer agrees with what the window processors already did using the advanced time. The new tests in test/time.test.ts only cover timers, not windows.

**Suggested fix:** Either keep Stream Time advanced for records skipped after processing began (revert to the earlier behaviour and update docs/limitations.md), or roll back everything that depended on the advanced time: have expire() and place() use a Stream Time that is committed only once the record succeeds, or move expiry to after the record has processed successfully. Add a Test Driver test with a throwing windowed aggregator, like the scenario above.

**Skeptic's evidence:** I reproduced this with the Test Driver in /Users/igorshalygin/.claude/jobs/e36bc646/tmp/winroll.test.ts (run with `npx vitest run --root <tmp> --silent=false`). The setup is a tumbling('1s') aggregate whose aggregator throws on 'bad', with the processing handler returning 'continue'. I piped a:x@100, a:y@200, b:z@300, b:bad@90000, then a:w@400.

Output: [a@0=x, a@0=xy, b@0=z, a@0=w]. Store afterwards: [[{a,[0,1000)},'w']].

So the closed window a@0, which had already emitted its final 'xy', reopens and emits 'w', and b@0's aggregate is lost.

Why it happens:
- src/task.ts:373-386: the Task calls advanceStreamTime(90000) before processing. On a processing error, onError restores only `streamTime` and the timer due times (`streamTime = before.streamTime`).
- src/streams-app.ts:1137-1138: process() calls expire() before update. expire() (streams-app.ts:1041-1049) has already deleted every window before firstKeptWindowStart(90000), and set keptFrom. None of that is undone when the record is skipped.
- Next record: place() (1031-1039) reads the rolled-back task.streamTime() (400), so a@0 is not late and is recreated from empty. keptFrom stays at its high value, so expire() returns early until Stream Time passes it again.

This contradicts the docs: docs/limitations.md:22 says a skipped record does not advance Stream Time, but the windows it expired stay expired. Stream Time and window state are now inconsistent.

## 7. [P3] Timers scheduled while processing a skipped record keep a due time based on the rolled-back Stream Time

- Area: store-task-dsl (claimed P3, reproduced: True)
- Files: src/task.ts:205-211 (schedule computes due from current streamTime); src/task.ts:374,384-385 (before.dues snapshot covers only pre-existing timers)

**Scenario:** A Processor schedules a 10 ms stream-time timer inside process() on its first record (lazy scheduling). The first record has timestamp 500 and throws, and the handler returns 'continue'. advanceStreamTime(500) has already run, so the new timer gets due=510. The rollback restores streamTime to undefined but leaves the new timer alone, because before.dues holds only the timers that existed before the record. Then records at 100, 105 and 110 arrive. advanceStreamTime only sets due when it is unset (??=), so the timer stays at 510 and does not fire at 110 as it would had the skipped record never been seen. More generally, any timer created during a skipped record keeps its schedule, measured from the skipped record's timestamp.

**Impact:** The skipped record still changes timer scheduling, contrary to the commit's claim (and docs/limitations.md) that a skipped record leaves Stream Time and timers as they were. Punctuations fire late, possibly much later if the skipped record had an outlier timestamp.

**Suggested fix:** In onError, also go through timers not listed in before.dues. Recompute their due from the restored streamTime (undefined if streamTime is undefined, so that the next advanceStreamTime sets it), or remove timers created during the skipped record if that is the intended meaning. Add a time.test.ts case that schedules from process().

**Skeptic's evidence:** Confirmed by reading the code and by a unit test. In src/task.ts, schedule() (lines 205-210) sets due = streamTime + intervalMs, using streamTime after advanceStreamTime(record.timestamp) has already run at line 375. The onError rollback (lines 384-385) restores streamTime and the due times in before.dues, but before.dues is a snapshot taken at line 374, so it holds only timers that existed before the record. A timer created during the skipped record keeps its due time. Restoring streamTime to undefined does not clear that due time, because advanceStreamTime (line 224) uses `timer.due ??=`. Test /Users/igorshalygin/.claude/jobs/e36bc646/tmp/lazy-timer.test.ts (run with `npx vitest run --root /Users/igorshalygin/.claude/jobs/e36bc646/tmp lazy-timer`) uses a Processor that schedules a 10 ms stream-time timer in process() on its first record. It then pipes a 'bad' record at ts 500 (skipped with 'continue'), followed by records at 100, 105 and 110. The test passes with ticks == [], so the timer never fires at 110: its due time stays 510. Had the skipped record never been seen, the first schedule call would run at streamTime 100, giving due=110 and a tick at 110. The same thing happens whenever any timer is created during a skipped record whose timestamp is above the current Stream Time: the punctuation fires late. This goes against the rollback comment ("What a skipped record must leave as it was: Stream Time and when its timers are due"). Impact is limited to lazy or in-process() scheduling, so P3.

## Refuted

- Containers on one host that share a stateDir have separate PID namespaces, so kill(pid, 0) probes the wrong process and a live lock is taken over (lock-protocol): The mechanism is real: isStale() at src/state-directory.ts:255-266 uses process.kill(lock.pid, 0) after a `booted` check, and BOOTED comes from os.uptime(), which is not namespaced, so containers on one node would agree on it. The claim still fails as a defect for three reasons. (1) The documented configuration rules it out. docs/workers.md:57 says "Give each process (container, host) its own state directory", which names containers explicitly. docs/operations.md:19 says "give it its own directory per process". The sharing allowance at operations.md:20 is for "processes that share one host", which means one OS process space, not separate containers that mount a common volume. Two containers sharing a hostPath stateDir goes against explicit guidance. (2) The fix commits did not add this. `git show 0150f80:src/state-directory.ts` already has the same PID+booted staleness check at lines 222-230 with kill(pid,0). The range changed operations.md only at lines 5 and 23; line 20 is unchanged. The task is to review the fix commits only. (3) I could not reproduce it without containers, and the setup needs a deliberate misconfiguration. At most it is a P3 doc note: say "one host" means one PID namespace. It is not a P2 regression from these commits.
