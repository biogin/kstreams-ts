**What to build:** A randomized crash test suite (ADR-0011) repeatedly SIGKILLs a single Worker running a stateful exactly-once app and checks that outputs and State Stores exactly match a reference run.

## Comments

- 2026-10-21: Done on branch `ticket/17-crash-suite`.
  - **Suite:** `test/crash/crash.test.ts`, App Module `test/crash/crash-app.ts` (exactly-once, `count()` and an order-sensitive checksum `aggregate()`, both on SQLite, 2–4 partitions, `commitIntervalMs` 20/50/100, `commitMaxRecords` 5–99), config `vitest.crash.config.ts`, script `npm run test:crash` (excluded from `npm test`, not part of `test:integration`). Settings: `KSTREAMS_CRASH_ITERATIONS` (default 4), `KSTREAMS_CRASH_KILLS` (default 5), `KSTREAMS_CRASH_SEED` (default random; iteration i uses seed + i). A failure prints the seed, plan, kills and the command that reruns that iteration. The defaults take about 3 minutes.
  - **Kills** (external SIGKILL only, one Worker, input produced throughout): `startup` (0–400 ms after running: Fencing, Restore, first commits); `after-commit` (committed offsets polled back to back, kill as soon as they advance: aims at the SQLite commit and Checkpoint that follow the Kafka commit); `boundary` (1–7 commit intervals ± 3 ms after a commit was seen); `uniform` (0–1000 ms).
  - **Oracle** (reference computed from the produced input): each key's committed outputs are exactly 1..n and its running checksums, in order; each Changelog's committed records per key are exactly the same sequences; all input consumed (committed offsets = records produced); after a graceful stop, the SQLite stores on disk hold the exact finals. Committed records are read by the suite's own reader (`test/crash/log-reader.ts`): a read_uncommitted fetch, with transactions resolved from the log's own control batches, so it trusts neither the client's read_committed filtering (platformatic/kafka#467) nor the engine's reader. Sanity check: with `guarantee: 'at-least-once'` in the fixture, the suite fails (duplicates in outputs, Changelogs and stores).
  - **Bug found, not fixed (out of scope): Restore's reader drops committed records.** The suite also reads every output topic and Changelog with `createChangelogReader` (`src/restore.ts`, which Restore uses) and compares the result with the log. Seed 991282543 (`KSTREAMS_CRASH_SEED=991282543 KSTREAMS_CRASH_ITERATIONS=1`) failed on both of its 2 runs, and about 1 in 8 iterations fails overall. Outputs, Changelogs and stores were exact according to the log. But `createChangelogReader` read only 3910 of the 3967 committed records of output partition 1 (the checksum topic was the same), and the first one missing was at offset 638. The log there: `618-636 transactional pid 5049 epoch 3`, `637 abort epoch 4` (the fenced zombie's transaction), `638-652 transactional epoch 5`, `653 commit epoch 5`, and so on. Every incarnation reuses the same producer ID (the transactional ID is per Worker number) with a bumped epoch, so one fetch response can hold several abort markers of one producer. Likely cause: the client's `#filterUncommittedMessages` keys aborted ranges by producer ID, so a later abort marker closes the range of an earlier aborted transaction (the "second marker closes the wrong range" defect in `.scratch/upstream/platformatic-kafka-read-committed-aborted/issue.md`). That drops the committed transactions in between, and abort marker 637 itself, so `AbortedTransactions` in `restore.ts` may also keep the producer open too long. Impact: a full Restore, or one from a Checkpoint before such a stretch, silently misses committed Changelog records and leaves wrong state. Fix direction: read Changelogs without the client's filter (read_uncommitted, or bypass it) and resolve transactions per response the way Java's `CompletedFetch` does. This ties in with the STATUS open items on the `restore.ts` filter and on the input path. Until it is fixed, the suite fails on this intermittently, on purpose.
