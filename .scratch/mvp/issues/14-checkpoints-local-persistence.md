# 14: Checkpoints and local persistence

**What to build:** SQLite files persist in `<stateDir>/<applicationId>/<task>/` across restarts. Restore replays only the part of the Changelog after the Checkpoint, and a store with a missing or unclean Checkpoint is wiped and rebuilt (ADR-0009).

## Comments

- **Module:** `src/checkpoint.ts` (`TaskCheckpoint`, `readCheckpoint`/`writeCheckpoint`/`removeCheckpoint`). Wired in `src/task.ts` (a Task that is restored and has a state directory keeps one for its persistent stores), `src/restore.ts` (`RestoringStore.checkpoint`; `restoreStores` resolves to the offset each store applied up to; `ChangelogReader.read(topic, partition, apply, from?)` resolves to the next offset, or undefined when `from` is outside the partition) and `src/worker.ts` (`BatchCommitter.commit` resolves to the produced offsets; `task.checkpoint(...)` runs after the commit; Tasks' stores are closed when the cycle ends).
- **Format:** one file per Task, `<stateDir>/<applicationId>/<task>/.checkpoint`, JSON `{"version":1,"offsets":{"<store>":"<next Changelog offset>"}}` (offsets as decimal strings, they're 64-bit). Written as `.checkpoint.tmp` + fsync + rename + directory fsync. Stores are flushed first (`StateStore.flush`; SQLite runs `wal_checkpoint(FULL)`, since `synchronous=NORMAL` doesn't sync on commit). `version` covers the Checkpoint, the SQLite layout and the key encoding (ADR-0015): another version counts as missing.
- **"Unclean":** a store may hold a write its Changelog up to the Checkpoint doesn't have. A Task's persistent stores are wrapped so that the first write after a Checkpoint removes the file (durably) before the write happens: a put/delete outside a store transaction, or a store transaction's `commit`. So the file exists only while the stores match it exactly. A store is wiped and fully restored when the file is missing (never written, or removed and the process stopped before the next one, e.g. a crash mid-batch), unreadable, of another version, doesn't list the store, or its offset is before the partition's start or past its end (e.g. a recreated topic). A clean `stop()` commits and checkpoints, so a restart replays only what came after.
- **Persistence is declared by the store:** new optional `StateStore.persistent` (and `flush()`). `stores.sqlite()` is persistent with a state directory; in-memory stores, SQLite without a directory and custom stores that don't declare it are fully restored (wiped) on every start and never checkpointed. Restore also writes a Checkpoint as soon as it's done.
- **Offsets:** the at-least-once committer takes the next offset from the broker's base offset plus the number of records sent to that Changelog partition (one record batch per partition per send). If a partition ever gets several base offsets it falls back to the last base + 1: a Checkpoint may be too low (replaying already-applied records is harmless), never too high.
- **Tests:** `test/checkpoints.test.ts` (Task + SQLite + fake Changelog: written per commit and after Restore, removed before the next write, restart replays only after it, wipe for missing/unreadable/other-version/unlisted/past-the-end, in-memory never checkpointed, no Checkpoint after a failure); `test/restore.test.ts` (partial Restore, positions); integration `Restore from the Changelog › restarts from the Checkpoint: replays only the Changelog records after it` counts store writes in the second run (1 replayed + 1 processed, not 4 + wipe) and checks the new Checkpoint; the missing-Checkpoint wipe test now removes the file. Integration tests that read in-memory stores after `stop()` wrap them with `keptOpen`, since stop now closes stores.
- **Concerns for ticket 16:** (1) `TransactionalCommitter.commit` returns no offsets yet (EOS + stores is still refused); it needs them from `transaction.send` results, and transaction markers mean "next offset" may point at a control record, which Restore skips (fine). (2) The guard treats a store transaction's `commit` as dirtying, so under EOS (SQLite transaction committed after the Kafka commit, then the Checkpoint) a crash between the two would wipe. That's correct but wasteful: there the Changelog already has everything the SQLite commit adds, so ticket 16 can let that commit not remove the Checkpoint (writes inside an open store transaction already don't). (3) Restore wipes/replays inside the Task's queue; with a store transaction open for the batch, Restore's own per-chunk transactions would nest, so Restore has to run before the batch transaction begins (already noted in 16). (4) The Checkpoint call is already after the Kafka commit in `CommitCycle.#commit`, so ticket 16 only has to put the SQLite commit between them. (5) No SIGKILL test with SQLite stores yet; the crash suite still uses in-memory stores.
